Internet Control Message Protocol (RFC 792)
defined in the RFC 792
provides control mechanisms for the IP
in case of IP datagram delivery problems respective ICMP
notifications may be sent to the sender
ICMP messages don’t have to be delivered; in fact most
administrators filter them out for security reasons

--- page 5 ---

ICMP Position in the TCP/IP Stack
According to the RFC 792:
ICMP, uses the basic support of IP as if it were a higher
level protocol, however, ICMP is actually an integral part of
IP, and must be implemented by every IP module.
Most analyzers show ICMP headers as upper layer headers,
analogously to TCP or UDP headers (protocol: 1).
In fact ICMP headers replace IP headers i.e. extend them with
additional fields.

--- page 7 ---

ICMP Header Parameters
Type – the reason for the IP packet delivery failure, selected
values:
8 and 0 – Echo Request/Reply,
3 – Destination Unreachable,
5 – Redirect Message,
11 – TTL Exceeded,
12 – Parameter Problem.
Code – more details on the problem; defined for any type
separately.
Checksum – analogous to similar fields in headers previously
introduced. Calculated for 16-bit word of ICMP headers
(beginning from the type field).

ICMP Destination Unreachable
Later RFCs (1122 and 1812) define 6-15 codes:
6 – Destination network unknown,
7 – Destination host unknown,
8 – Source host isolated (not used),
9 – Destination network administratively prohibited,
10 – Destination host administratively prohibited,
11 – Destination network unreachable for ToS,
12 – Destination host unreachable for ToS,
13 – Communication administratively prohibited by filtering,
14 – Host precedence violation,
15 – Precedence cutoff in effect.

--- page 22 ---

Host Connectivity – ping
available in Linux/Unix and Windows
sends ICMP ECHO REQUEST packets and expects
ECHO REPLY packets from the destination
based on replies estimates delays and packet loss
many administrators filter ICMP packets (including ICMP
ECHO) on routers so lack of ping replies doesn’t imply
communication problems

--- page 23 ---

Pinging the loopback
Pinging loopback addresses (127.0.0.0/8) helps ensure that the
TCP/IP stack works correctly.
Reminder: Every TCP/IP host corresponds to any 127/8
address and the name localhost should be assigned with the
address: 127.0.0.1:
/etc/hosts (Unix/Linux)
C:\Windows\System32\drivers\etc\hosts (Windows)

--- page 24 ---

Host Connectivity – traceroute
available in Unix/Linux (in Windows: tracert)
sends series of UDP packets to port 33434 of the destination3
with TTL values set to 1, 2, 3, . . . and analyzes ICMP
TIME EXCEEDED notifications from routers
based on replies tries to estimate packet routes and delays at
hops
both UDP packets addressed to the port 33434 and ICMP
packets can be filtered out at border routers so lack of replies
doesn’t imply communication problems
3Usually sending packets to different port or ICMP ECHO packets is possible.

--- page 26 ---

Packet Analyzers
API for programs used throughout this course is provided by the
pcap. Respective Linux/Unix library is called libpcap. The
Windows port is a WinPcap. Pcap is utilized by the following
tools:
tcpdump (Windows – WinDump, Solaris – snoop),
wireshark,
nmap
arping (Habets),
snort (Network Intruder Detection System).
Using pcap requires setting network interface cards in so-called
promiscuous mode which can be done only by superusers (root,
administrator, etc.)

--- page 27 ---

Packet Analyzer – tcpdump
pcap-filter expression syntax – the same as capture filter in wireshark
Save ESMTP packets exchanged between this host and hosts from other
networks to plik.pcap
# tcpdump ’(not net 194.29.178.0/24 or host 194.29.178.22) and \
(port 25 or 465 or 587)’ -w file.pcap
Save incoming TCP packet with SYN or FIN flags . . .
# tcpdump ’dst 194.29.178.22 and \
(tcp[tcpflags] & (tcp-syn|tcp-fin) != 0)’ -w file.pcap
. . . or just display first 64 bytes decoded
# tcpdump ’dst 194.29.178.22 and \
(tcp[tcpflags] & (tcp-syn|tcp-fin) != 0)’ -n -vv -s64

## Objective of the work: 
The objective of the thesis is to design, implement, and evaluate a configurable web application that supports creation of laboratory assignments for academic courses using Retrieval-Augmented Generation (RAG). The application will generate structured, evidence-grounded assignments from user-provided course materials according to configurable pedagogical requirements. The solution will be evaluated using Operating Systems course materials as a case study through a reproducible comparative analysis of baseline vector RAG, Hybrid RAG, LightRAG, and GraphRAG with respect to retrieval relevance, source traceability, factual correctness, learning outcome alignment, latency and estimated inference cost. The outcome will be a documented and deployable web application for instructors, together with a reproducible evaluation benchmark, automated test suite, experiment configurations and aggregated evaluation results. 
 
## Subject of submitted work: 
### Corpus preparation. 
Identify permitted course materials, document their formats, and define corpus inclusion and exclusion rules. Prepare two separate local knowledge bases: a primary knowledge base containing authoritative materials for the target course and a supplementary knowledge base containing approved materials from related or earlier courses. The application shall not use web search. 
### Storage, ingestion, metadata, and indexing. 
Implement persistent storage for source documents, extracted text, metadata, vector embeddings and indexes, generated assignments, claim-to-evidence links, benchmark requests, experiment configurations, execution logs, and evaluation results. Implement ingestion for PDF, HTML, TXT, and Markdown documents; extract text and assign metadata; segment documents; and build searchable indexes. Each indexed fragment shall retain a source identifier and retrievable text excerpt. Metadata shall include, where available, knowledge-base type, course, document type, topic, version, learning outcomes, difficulty level, and authority level. 
### Benchmark and evaluation protocol. 
After the corpus is finalized and before implementation or tuning of the compared architectures, define evaluation metrics, an expert-assessment rubric, and a held-out benchmark. Freeze a held-out benchmark of at least 60 requests, with at least 8 requests in each of the following categories: supported single-source requests, multi-source requests, requests requiring permitted supplementary materials, unsupported requests, conflicting-source requests, and requests representing different difficulty levels or course stages. The benchmark shall not be used for prompt development, configuration tuning, or architecture selection. 
### Baseline retrieval pipeline. 
Implement a baseline vector RAG pipeline with configurable retrieval parameters and metadata filters. Primary-course materials shall be prioritised. Mandatory technical requirements, course-specific tools, learning outcomes, and assessment criteria shall be supported by primary-course materials. Supplementary materials may be used only for contextual explanations, prerequisites, hints, or optional extensions, and shall not override primary-course materials. 
### Comparative retrieval architectures. 
Implement Hybrid RAG, LightRAG, and GraphRAG using the same corpus, generation model, prompt template, output schema, validation procedure, benchmark, and evaluation protocol as the baseline. The embedding model, metadata policy, retrieved-context budget, and evaluation environment shall remain constant unless their variation is explicitly included as a documented experimental factor. Document any unavoidable deviations. For GraphRAG, evaluate whether relation type, relation weight, and graph-centrality measures improve assignment structuring compared with the baseline: concepts identified as central or pedagogically essential shall be candidates for core tasks, while concepts connected through weaker or supporting relations shall be candidates for prerequisites, contextual explanations, hints, or optional extensions. 
### Assignment generation and validation. 
Provide configuration of topic, learning outcomes, difficulty level, course stage, target competencies, expected duration, and assignment format. A completed assignment shall contain a title, prerequisites, objectives, environment and tools, tasks, submission requirements, assessment rubric, and source evidence. Each substantive technical claim and each mandatory task requirement shall be linked to at least one retrieved source excerpt and source-document identifier. Before presentation, the application shall validate the output schema, mandatory sections, source-reference validity, and evidence coverage of mandatory requirements. If required evidence is unavailable, contradictory, or fails validation, the application shall return a structured response stating the reason and shall not present the output as a complete assignment. 
### Web application. 
Deliver an instructor-facing web application providing document and metadata management, corpus and index preparation, assignment configuration, generation, inspection of retrieved evidence, section-level editing and regeneration, and export. The standard mode shall use the architecture selected through comparative evaluation. An optional experimental or administrator mode may allow reproduction of results for the evaluated architectures. 
### Testing and acceptance criteria. 
Implement automated tests for supported file formats, ingestion, metadata filtering, source traceability, output-schema validation, unsupported requests, conflicting evidence, and repeated-generation scenarios. Validate factual correctness, learning-outcome alignment, and educational usefulness using the predefined expert-assessment rubric. On a manually annotated subset of at least 60 generated claims, evaluate the evidence-validation mechanism by reporting precision, recall, and F1-score for classification of claims as supported, contradicted, or unsupported. Report unsupported-claim rate before and after validation. 
### Comparative evaluation. 
Report retrieval relevance, evidence coverage, citation correctness, unsupported-claim rate, output-schema compliance, learning-outcome alignment, factual correctness, expert-rated usefulness, latency, indexing time, storage use, token usage, and estimated inference cost. Select the default architecture according to a predefined decision rule prioritizing grounding, factual correctness, and learning-outcome alignment, while considering operational cost. 
### Deployment and result. 
Deliver a tested, documented, and deployable web application for evidence-grounded generation of laboratory assignments from closed course-specific knowledge bases, including source code, deployment instructions, configuration files, reproducible experiment scripts, benchmark materials, evaluation rubrics, and aggregated results. The application, source code, configuration files, benchmark materials, evaluation scripts, aggregated results, and documentation may be archived in the Warsaw University of Technology repository.
